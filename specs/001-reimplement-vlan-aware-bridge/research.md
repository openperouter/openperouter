# Research: Existing-API VLAN-Aware VNI Reimplementation

**Date**: 2026-10-27
**Scope**: Planning research only. No deployment or runtime tests were performed.

## 1. Dedicated domains and fixed internal VLAN

**Decision**: Use VLAN ID 1 on every dedicated Linux VNI bridge. Keep all current public API/static types and conversion params.

**Rationale**: The requested change is internal. Dedicated bridges keep VLAN reuse independent and preserve the full VNI range. Existing `VNIParams` already supplies VNI, VRF, namespace, VTEP, port, and overhead; `L2VNIParams` adds gateways and host attachment (`internal/hostnetwork/vni.go:29`, `internal/conversion/host_conversion.go:278`). Static resources embed the current API specs (`api/static/config.go:23`). No field or allocation record is needed.

**Alternatives considered**: Shared bridges/pools introduce capacity and persistent ownership concerns outside scope. Equating VLAN IDs with VNI numbers would break valid VNIs above 4094. Future trunk abstractions provide no current value.

## 2. Preserve the neighbor-owning interface name

**Decision**: Preserve `br-pe-<VNI>` as the routed endpoint. Add `br-vl-<VNI>` for private switching. For L2 gateways, use an addressless `svi<VNI>` VLAN interface and a `br-pe-<VNI>` private macvlan carrying the current gateway addresses/MAC. For addressless L2/L3 domains, `br-pe-<VNI>` is the VLAN interface itself.

**Rationale**: `e2etests/tests/bridgerefresh.go:458` explicitly queries STALE neighbors on `br-pe-*`. The refresher uses that name for both neighbor lookup and ICMP device binding (`internal/hostnetwork/bridgerefresh/refresher.go:54`, `neighbor.go:17`, `ping.go:43`). Merely retaining the name on an addressless switching bridge would fail unchanged tests. `e2etests/tests/resiliency.go:507` also asserts forwarding entries on `vni110`, so that name stays.

**Alternatives considered**: Renaming e2e expectations violates acceptance. Adding a compatibility dummy interface would not own the actual neighbors. Direct anycast addresses on the SVI could remove one interface, but the selected macvlan layout separates gateway identity from router identity and matches the reference's gateway guidance.

## 3. VLAN routing and MAC identities

**Decision**: Put VRF membership on routed VLAN/gateway devices, not on private switching bridges. Keep a node-local router MAC distinct from the existing per-VNI anycast MAC. Add a local gateway FDB entry and preserve learning/suppression settings.

**Rationale**: FRR discovers VNI/VRF relationships from kernel interfaces. Its VLAN-aware examples use VLAN SVIs, VLAN-to-VNI tunnel mappings, receive-filter entries, and an optional macvlan for anycast gateways. These support the selected topology; the dedicated-bridge naming and VLAN reuse are this project's design choices. [FRR 10.6 EVPN documentation](https://docs.frrouting.org/en/stable-10.6/evpn.html#vlan-filtering-bridge-and-single-vxlan-device)

Current code binds the bridge to the VRF (`internal/hostnetwork/bridge.go:25`) and puts gateway addresses on it (`internal/hostnetwork/vni.go:210`). Those responsibilities move to the routed endpoint. Preserve the gateway MAC generated by `BridgeFixedMAC` (`bridge.go:100`). Keep node-local router MACs stable for the lifetime of their devices, including repeated reconciliation.

**Alternatives considered**: Keeping VRF membership on the backing bridge does not express the new VLAN relationship. Reusing the deterministic gateway MAC as every node's router MAC conflates their identities. Rewriting routing policy is unnecessary: `internal/conversion/frr_conversion.go:207` already relies on kernel discovery.

## 4. Fill the pinned netlink gap without dependency churn

**Decision**: Add a private, narrowly scoped rtnetlink helper using existing `netlink/nl` and x/sys. Keep netlink v1.3.1.

**Rationale**: The pinned library supplies VLAN filtering, membership, tunnel mapping, VLAN/macvlan links, and `Vxlan.FlowBased`, but does not expose vnifilter creation or receive-filter add/dump/delete. FlowBased creation normalizes the link VNI to 0, so `checkVXLanConfigured` must no longer equate `VxlanId` with the configured VNI. Verify the VNI through both mapping and receive-filter state instead. [Pinned netlink types](https://github.com/vishvananda/netlink/blob/v1.3.1/link.go), [pinned Linux implementation](https://github.com/vishvananda/netlink/blob/v1.3.1/link_linux.go)

Create external and vnifilter together in `RTM_NEWLINK` nested `IFLA_LINKINFO` / `IFLA_INFO_DATA`. Linux 5.18 requires collect-metadata and rejects changing vnifilter on an existing link. The upstream 5.18 implementation contains this capability; runtime verification is still required on the actual host kernel. [Linux VXLAN implementation](https://raw.githubusercontent.com/torvalds/linux/v5.18/drivers/net/vxlan/vxlan_core.c)

Use a small `RTM_GETLINK` parser to read the vnifilter flag ignored by the pinned link parser. For receive-filter entries, use `RTM_NEWTUNNEL`, `RTM_GETTUNNEL`, and `RTM_DELTUNNEL` with an AF_BRIDGE tunnel header and nested single-VNI entry. x/sys provides message/creation constants; serialize the 8-byte tunnel header locally and define only missing UAPI constants with source references. Validate response lengths, nesting and errors. Preserve IPv4/IPv6 source-address encoding and network-byte-order destination port. [iproute2 VXLAN encoding](https://raw.githubusercontent.com/iproute2/iproute2/main/ip/iplink_vxlan.c), [iproute2 VNI-filter encoding](https://raw.githubusercontent.com/iproute2/iproute2/main/bridge/vni.c)

**Alternatives considered**: FlowBased alone omits required filtering. Creating then enabling vnifilter is invalid. A dependency upgrade broadens scope without need. Shelling out for core provisioning adds a runtime executable/parse contract when existing rtnetlink primitives suffice. Do not build a general netlink library.

## 5. Reconcile complete state and rebuild owned legacy devices

**Decision**: Check link attributes and mutable membership/mapping/filter/FDB state separately. Add a kernel-only legacy preflight before new VXLAN creation; remove owned legacy VXLANs as a group, then obsolete owned router bridges, preserving host-side attachments where possible.

**Rationale**: Existing `createVXLan` compares immutable fixed-ID properties and recreates mismatches (`internal/hostnetwork/vxlan.go:46`). Matching metadata link properties alone cannot detect a missing VLAN mapping or receive filter. Existing bridge/MAC/link helpers already avoid unnecessary writes because they can flush neighbors (`bridge.go:112`, `link_properties.go`). Preserve that behavior.

The reference identifies incompatible legacy/VLAN-aware same-port coexistence. Sequentially replacing only the first L3VNI while legacy L2VNIs remain can therefore fail before convergence. Remove the owned legacy devices first; a brief rebuild is consistent with the spec's exclusion of hitless conversion. Ownership is established by known prefixes/types in the target namespace, never by UDP port alone. Retry incomplete setup using normal desired-state reconciliation. Existing per-resource errors remain `OverlayAttachmentFailed`; status construction remains unchanged (`internal/controller/routerconfiguration/host_config.go:90`, `status.go:13`).

**Alternatives considered**: A persisted migration/version registry is unnecessary derived state. Silent fallback violates the replacement requirement. Deleting unrelated VXLANs or external host bridges violates ownership. Rebuilding matching devices on every reconcile risks route/neighbor loss.

## 6. Cleanup, MTU and Grout boundaries

**Decision**: Extend owned namespace cleanup to VLAN/macvlan links and the new bridge prefix; retain existing host-side lifecycle. Preserve payload MTU calculations and separate Grout provisioning.

**Rationale**: `removeNamespaceSideVNIs` currently handles only bridges and VXLANs (`internal/hostnetwork/vni.go:337`). Child devices and new names need explicit ownership-aware cleanup, including partial setup and underlay replacement. Internal VLAN classification must terminate before VXLAN encapsulation, preserving existing 50-byte IPv4 / 70-byte IPv6 overhead and mixed SRv6 tests. Grout uses shared naming/MAC helpers and refresher but independent setup (`internal/grout/l2vni.go:42`, `internal/controller/routerconfiguration/grout_config.go:81`). Do not change those shared helper results.

**Alternatives considered**: Subtracting another four bytes without an actual on-wire VLAN header would lower existing MTU behavior. Unconditionally switching shared names would regress Grout. A new dataplane interface abstraction is unnecessary.

## 7. Verification baseline and executable entry points

**Decision**: Use `make test`, `make lint`, unchanged pod/host e2e suites, the static-before-API boot lane, and existing Grout regression/packaging lanes. Copy existing CI filters as the compatibility baseline.

**Rationale**: Hostnetwork tests require `runasroot`; ordinary `go test` omits them. `Makefile:100` compiles race-enabled privileged binaries and runs them in an OVS-enabled container. `Makefile:360` defines `make e2etests` (plural), despite older prose mentioning another spelling.

`.github/workflows/ci.yaml:388` has the current hostmode exclusions. The e2e skill's hostmode text is broader/stale; using it verbatim could silently reduce coverage. During execution use deploy/e2e skills, explicitly retaining the CI filters documented in quickstart. Keep all existing packaging lanes and exclusions unchanged.

**Alternatives considered**: Focused e2e runs help diagnosis but cannot replace the full acceptance run. Benchmarks and new trunk tests are outside scope. Planning does not establish runtime compatibility: initial privileged tests must prove the chosen gateway chain, filter encoding, same-port dispatch and neighbor ownership before broad integration work.

## Research disposition

All design questions are resolved. Runtime proof is assigned to implementation, with failure requiring a design correction within the unchanged API/e2e boundary. No unresolved clarification is carried into Phase 1.
